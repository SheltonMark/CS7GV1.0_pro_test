## 1. 参考实现的完整链路（已逐行核实）

核心类 `TencentIotMgr`（`src/Common/TencentIotMgr.{h,cpp}`），六步：

| # | 步骤 | 出处 |
|---|---|---|
| 1 | 全局初始化：`setUserCallbackToXp2p(avRecvCb, msgCb, deviceDataCb)` → `setQcloudApiCred(app_id, app_key)` → `setLogEnable(false,false)` → `InitVlc()` | `TencentIotMgr.cpp:71-84`（`InitTencent`） |
| 2 | 取流凭证：`RequestManage::GetXP2PINFO_External(productKey, deviceName, &xp2pInfo)`，走**腾达后台**（非腾讯云 API） | `:169-176` |
| 3 | 建联：填 `app_config_t{server:"", ip:"", port:20002, type:XP2P_PROTOCOL_AUTO, cross:false}` → `startService(deviceName, productKey, deviceName, config)` | `:178-194` |
| 4 | 灌凭证：`setDeviceXp2pInfo(deviceName, xp2pInfo)`；**失败必须 `stopService` 回滚** | `:196-202` |
| 5 | 等就绪：异步回调把 state 推到 `XP2PTypeDetectReady`，超时 **10 秒**（`QEventLoop` 阻塞等待） | `:207+`（`waitXp2pReady`） |
| 6 | 取播放地址：`delegateHttpFlv(deviceName)` 返回**本地 base URL**，拼 `ipc.flv?action=live&quality=<主/子>` → 交播放器 | `:316-336`（`composeLiveUrl`） |

关联事实：
- **回放同源**：`composePlaybackUrl` 只是把参数换成 `ipc.flv?action=playback&channel=N`（`:349-352`）。产测不需要回放，但说明同一条通路可扩展。
- **分支已核实**：`Common`（最新，`e7202b9` @08-13）是正确分支，但该提交只加了 `src/test.txt` 一行、无实质内容 ⇒ **真实最新实现是 `8948b9e`「删除废弃的 TencentMgr，全面改用 TencentIotMgr」**。本方案参考的 `TencentIotMgr` 即当前唯一在服役的实现，未引用已废弃代码。相关历史：`a3ba3e9` 加拉流超限检测（见 §1.2）、`3333d26` 屏蔽腾讯设备对讲按钮、`82f323b`/`98914f7` 设备列表 30s 轮询。

### 1.1 XP2P 数据通道（第二条通路，产测**暂不使用**但需知道）

除 HTTP-FLV 流之外，XP2P 还有**同步命令通道**：`TencentIotMgr::SendCommand(iotId, command, recvOut, timeoutUs)` 底层是 `postCommandRequestSync`（`:375-408`），承载设备私有协议，形如
`action=inner_define&channel=0&cmd=get_device_st&type=…&qualtity=…`（注意 `qualtity` 是设备侧的拼写错误，照抄才通）。

⚠️ **不要照搬到产测**：这是 App 侧固件的私有命令集，我们的 AOV 设备**未实现 `inner_define`**（产测协议一律走云端物模型物 5 条 action）。若照抄超限检测，在我们设备上会**超时失败**。
✅ **价值**：万一后台授权卡死（§2.2），这条通道是"PC 直连设备下发命令"的技术可能性——但需设备端新增实现，属**另一个课题**，不在本期。

### 1.2 拉流路数超限（产线多工位并行的真实风险）

App 侧专门加过检测（`a3ba3e9`）：拉流前用上述通道查 `get_device_st`，解析返回 JSON 数组第 0 项的 `status` 与 `maxConnectNum`——**`status="0"` 可拉流、`"1"` 即超限**，超限则关闭 XP2P 并提示 UI；JSON 解析失败按"允许播放"放行。

对产测的含义：
- **单台设备的并发拉流是有上限的**（`maxConnectNum`）。产线若出现"同一台设备被两个工位/两台电脑同时拉"（例如调焦工位没退出、成品工位又拉），会拉不上且现象诡异。
- **产测侧对策（不依赖设备私有命令）**：① 工位切换/离开页面**强制 `stop()`**（本来就要做，见 §4）；② 会话内保证"同一时刻只有一路流"；③ 拉流失败时给出明确提示「可能被其他工位占用」，而不是笼统的"拉流失败"。
- 若后续确有必要精确探测，再评估让设备端实现一个产测版状态查询（走物模型或数据通道），**本期不做**。
- **对讲通路不存在**（`3333d26` 已屏蔽腾讯设备对讲按钮）⇒ 咪头测试只能靠"PC 端听设备上行音频"，与评审 §4.5 定的口径一致，无第二选择。
- **回调线程安全**：`msgCb` 是 C 回调、在 SDK 线程触发，参考实现用 `QMetaObject::invokeMethod(..., Qt::QueuedConnection)` 弹回主线程（`:60-67`）。这个模式必须保留。
- **凭据硬编码**：`sg_app_id` / `sg_app_key` 直接写在 `InitTencent`（`:72-73`）。产测工具应改为配置项（管理员可见），不写死在代码里。

### 关键结论：播放侧只需要能播 HTTP-FLV

第 6 步产出的是**本机 URL**（XP2P SDK 在本地起了转发服务），不是 P2P 私有流。**播放器与 XP2P 完全解耦**——这是整合方案的最大有利条件：播放实现可以自由更换，不影响建联逻辑。

## 2. 三个硬约束（决定方案形态）

### 2.1 ABI：MSVC 库 vs MinGW 工具链 ⚠️ 最大风险

参考工程的三方库是 MSVC 惯例的 `.lib`（`TSS.pro:78-82` 的 `VLCQtCore.lib`；`:110-117` 的 `-lapp_interface`），而本工具是 **MinGW GCC 13.1**（`build.sh:22`）。

- **XP2P（`app_interface.dll`）**：纯 C 接口 ⇒ **C ABI 跨编译器兼容**。MinGW 可用两种方式接：① 用 `gendef`/`dlltool` 由 DLL 生成 `.a` 导入库；② **运行时 `LoadLibrary` + `GetProcAddress` 手动绑函数指针**（推荐——彻底绕开导入库，且 SDK 缺失时能优雅降级为"拉流不可用"而不是整个程序起不来）。
- **VLCQt（`VLCQtCore.lib`）**：C++ 库 ⇒ **C++ ABI 不兼容，MinGW 无法链接 MSVC 编译的 C++ 库**。加上 VLCQt 本身是 Qt5 时代产物、已基本停维护，**此路不通**，必须换（见 §3）。

### 2.2 后台授权（P0，非技术阻塞）

取流凭证走腾达后台 `GetXP2PINFO_External`，需 `Authorization: Bearer access_token` ⇒ **必须登录腾达账号**。产线上的新机**未绑定任何账号**，后台是否允许取流未知——这是读代码定不了的事，须后台同事确认（已在 `PC客户端-后台授权确认清单.md`）。方案对两种结果都留了退路（§5）。

### 2.3 产测的画质诉求与消费级不同

调焦要看清**清晰度边界**，所以：优先主码流（`quality` 参数）、低延迟优先于流畅（宁可丢帧不要缓冲堆积）、需要构图辅助线（UI 已实现三分法）。这决定播放器参数取向（§3.3）。

## 3. 播放层选型：三条路，建议 A（先做 spike 验证）

### 方案 A（推荐）：Qt 6 原生 `MediaPlayer` + `VideoOutput`

QML 里直接给 URL，Qt 6.5+ 默认 FFmpeg 后端。

- ✅ 零三方依赖、QML 原生集成（`VideoOutput` 就是个 Item，直接嵌进 `ViewFocus.qml` 的预览区）、随 Qt 更新、部署简单（`windeployqt` 自动带）
- ⚠️ **唯一未知：FFmpeg 后端对 HTTP-FLV 的支持**。FFmpeg 本身支持 flv demux，但 Qt 的封装是否放行、直播流是否稳定，**必须实测**
- 音频：`MediaPlayer` 默认解码播放，咪头听声天然满足

### 方案 B（退路）：libVLC C API + QML video sink

不要 VLCQt 壳，直接用 `libvlc_*` 的 **C 接口**（C ABI，MinGW 可用；同样建议 `LoadLibrary` 动态加载）。

- ✅ VLC 播 HTTP-FLV 是成熟能力，参考实现已在服役 ⇒ 风险最低
- ⚠️ 需要自己把解码帧喂给 QML（`libvlc_video_set_callbacks` → `QVideoFrame`/`QQuickItem` 自绘），工作量比 A 大 2–3 人日；部署需带 VLC 的 `plugins/` 目录（参考实现就在 `applicationDirPath()/plugins`，`:88-96`）

### 方案 C（保底）：外部播放器进程

调用系统 VLC/ffplay 打开 URL，另开窗口。

- ✅ 半天可用，联调期能立刻验证"流通不通"
- ❌ 不能嵌入界面、体验割裂，**只作为 spike 期的验证手段**，不作为交付形态

### 3.3 播放参数（不论 A/B 都要设）

低延迟优先：网络缓冲设到最低可用值（VLC 侧 `:network-caching=200` 量级；Qt 侧无直接旋钮，靠后端默认）；关闭字幕/多轨探测；主码流优先。

## 4. 整合架构（落到本工程的模块划分）

C++ 侧新增两层，QML 只拿到一个 `videoSink`/`MediaPlayer` 和几个状态属性：

```
QML ViewFocus.qml
   └── StreamController (QObject, 暴露给 QML)
         ├── 属性: state(Idle/Connecting/Ready/Playing/Error) / errorText / quality
         ├── 方法: start(productKey, deviceName) / stop() / setQuality()
         └── 组合两个下层:
             ├── Xp2pClient  —— 动态加载 app_interface.dll，封装 §1 六步
             │     · 回调用 QMetaObject::invokeMethod 弹主线程（照搬参考实现）
             │     · **不要 QEventLoop 阻塞等待就绪**：改为信号 + 超时定时器
             │       （参考实现用嵌套事件循环，在 QML 单线程界面里易引发重入）
             └── PlayerBackend —— 方案 A 即薄封装 QMediaPlayer；方案 B 为 libVLC
```

**与既有工位流程的关系**：
- 拉流是**长驻会话**（调焦工位全程开着），与产测指令的"逐条下发-等结果"互不干扰；设备端产测态是常电，不存在休眠打断流的问题。
- 咪头测试 = 拉流状态下下发喇叭放音（`Item=7`），工人听 PC 音箱 ⇒ **喇叭+咪头+音频链路一步三验**（见外设补充提示词）。所以播放层**必须保证音频可闻**（方案 A/B 都满足；若走方案 C 也需确认外部播放器不静音）。
- 切设备/离开工位必须 `stop()`：顺序为**先停播放器、再 `stopService`**（参考实现 `CloseXP2P` 即先关播放再停服务，`:355-372`）。反序有释放竞态风险。

## 7. 不照搬参考实现的四处（有意偏离）

1. **就绪等待去掉嵌套 `QEventLoop`**（参考实现 `waitXp2pReady`/`BuildPlaybackUrl` 用 `loop.exec()` 阻塞）——QML 界面里嵌套事件循环容易引发重入与假死；改为信号 + `QTimer` 超时（保留 10 秒量级）。
2. **XP2P 用动态加载而非链接导入库**——绕开 ABI 问题，且 SDK 缺失时降级为"拉流功能不可用"，不影响产测其余工位（产线上宁可少一个功能，不要整个工具起不来）。
3. **不用 VLCQt**——Qt5 时代库、停维护、C++ ABI 不兼容；改 Qt6 原生或 libVLC C API。
4. **app_id/app_key 不硬编码**——移入配置（超级用户可见/可改），与后台 API 凭证同一处管理。

## 8. 已知风险清单

| 风险 | 影响 | 处置 |
|---|---|---|
| Qt6 FFmpeg 后端不支持 HTTP-FLV | 方案 A 作废 | 步骤 3 提前验证，退方案 B |
| 后台不允许未绑定设备取流 | 调焦/咪头两项工位不可用 | 后台授权确认；退路 = 产线先绑一个产测专用账号（需产测与后台同意） |
| XP2P SDK 版本与后台 `xp2p_info` 格式不匹配 | 建联失败 | 索取时确认 SDK 版本，与 App 团队现网一致 |
| MinGW 下 `app_interface.dll` 有隐式 MSVC 运行时依赖 | 加载失败 | spike 阶段验证；必要时随包带 VC++ 运行时 |
| 部署漏 DLL/插件目录 | 产线机上黑屏 | 沿用 `build.sh` 的完整性自检思路，把新增 DLL 纳入检查 |
| **同一设备被多工位并发拉流超限**（`maxConnectNum`，见 §1.2） | 拉不上流且现象诡异 | 工位切换强制 `stop()`、会话内单路流、失败提示"可能被其他工位占用" |
| 照抄 App 的 `inner_define` 私有命令 | 在我方设备上必然超时（未实现） | 见 §1.1 警示；产测一律走云端物模型 |
