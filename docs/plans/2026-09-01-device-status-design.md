# 腾讯云设备名单实时状态修复设计

## 问题与实测证据

IoT Explorer 的 `DescribeDevices` 在当前产品下能返回设备名单，但所有设备的
`Status` 都是 `null`。旧代码对 `null` 调 `toInt()`，被当成 `0`，所以所有设备
都显示离线；第一次修正又错误地把该字段套成另一套三值枚举，导致全部显示未激活。

2026-09-01 使用当前 `cloud_config.json` 直接调用腾讯云 API 验证：

- 批量 `DescribeDevices`：5 台设备的 `Status` 全部为 `null`。
- 单台 `DescribeDevice`：按设备返回 `0/1/2/3` 状态，结果与腾讯云控制台一致。
- 腾讯云 IoT Explorer 官方 SDK 定义：`0=离线、1=在线、2=获取失败、3=未激活`。

## 设计

`TencentApiTransport::describeDevices()` 仍先调用一次 `DescribeDevices` 获取设备名，
然后针对名单中的每台设备并发调用 `DescribeDevice` 补齐实时状态。所有单台请求完成
后，沿现有 `CloudReplyHandler` 一次性返回完整名单，不修改 `ICloudTransport` 接口。

统一向上游传递整数 `status`：

- `0`：离线
- `1`：在线
- `2`：状态未知（云端返回“获取失败”，或者该台请求失败/字段缺失/异常）
- `3`：未激活

同时保留派生的 `online` 布尔值，兼容现有自动跳台逻辑。单台查询失败只影响该台，
不会让整个名单刷新失败。

## 界面行为

`CloudClient` 把 `status` 传到 QML。`DevicePicker` 分别显示“在线”“离线”
“未激活”“状态未知”；只有在线设备允许选择。点击未激活设备提示检查三元组，
点击状态未知设备提示刷新或检查云 API；离线设备仍提示检查工装卡和上电。

## 性能与失败处理

一批通常 5–15 台，单台状态查询并发执行，刷新耗时接近最慢的一次请求，而不是
串行累加。名单刷新仍保持 15 秒周期。若批量名单接口失败，沿用原有整体失败；若
单台查询失败，该台显示“状态未知”，其他设备照常可用。

## 验证

- 单元测试覆盖 `0/1/2/3`、null、缺失和越界状态的规格化。
- 实际 API 结果与腾讯云控制台逐台对照。
- 运行项目测试和 `build.sh`，确认 `dist/ProductTestTool.exe` 更新。
