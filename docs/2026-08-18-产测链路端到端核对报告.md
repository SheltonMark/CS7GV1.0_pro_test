## 3. 断点清单（按优先级）

### ① 阻塞级：空值解析拒绝

**位置**：`battery_ipc/app/cloud/cloud_action_mapper.cpp:52-55`

```cpp
if (item.empty() || eq == std::string::npos || eq == 0 ||
    eq + 1 >= item.size() || item.find('=', eq + 1) != std::string::npos) {
    return false;          // ← 任一项值为空 ⇒ 整条 params 被拒
}
```

**触发链**：codegen 桥无条件拼 `text=%s`（`tencent_generated_iv_usrex_callbacks.c:1905-1913`）
→ PC 恒发 `Text` 字段即便为空（`cloud_client.cpp:144`）→ 主流程恒传 `""`：

- `SequentialTestPanel.qml:67-68`——**每一条自动外设测试项**
- `ViewFinished.qml:254`——IMEI 查询

**后果**：设备收到 `item=0;operation=1;param1=100;param2=0;text=;request_id=42`，
在 mapper 就被拒，**不进 `ptest_submit_`、不写 ProductTestResult**。PC 干等满 15 秒超时，
除设备端一行日志外无任何诊断信息。

**逐 action 影响**（按解析规则模拟验证）：

| Action | 空值场景 | 结果 |
|---|---|---|
| PeripheralTest | `Text=""`（主流程恒发） | **拒** |
| WriteIdentity | 任一字段为空 | **拒** |
| WriteSuid | `Suid=""` | 拒 |
| WriteStage | `Timestamp=""` | 拒（实践安全，恒传真时间戳） |
| ClearPartition / Shutdown | 纯整型字段 | 通过 |

**写身份为何是结构性问题**：PC 的"空字段不下发 = 设备端保持原值"语义
（`cloud_client.hpp:62-64`）**必然**产生空值。而 `ViewFinished.qml:144-148` 从
`Session.batchRecords` 一次性传全部 8 个字段——**客户 InputData 文件里任何一列为空**
（Language、Uuid 最可能）**整条写身份就被拒**。表现为"随文件而变的间歇故障"，
不像代码 bug，排查会很痛。

**修法**：改 `ParseKeyValuePairs` 接受空值（`eq + 1 >= item.size()` 这一条去掉）。
mapper 侧 `ReadString(params, key, "")` 本来就把缺键当空串处理，语义已经对。
**不要动两端契约**、不要让 PC 改成"空字段也填占位符"。

### ② SupportedItems 三值不一致，3 项无执行体

`BuildCs7gPeripheralRegistry`（`peripheral_executors.cpp:333-370`）只注册 7 项执行体：
StatusLed(0)、InfraredLight(1)、WhiteLight(2)、Battery(5)、Speaker(7)、Cellular(9)、SdCard(10)。

| 来源 | 值 | 含 4/6/8？ |
|---|---|---|
| 真机注册表 | **1703** | 否 |
| `mock_transport.cpp:30` | **2037** | **是** |
| `MockData.qml:80` 兜底 | 1701 | 否 |

**复位按键(4)、云台(6)、咪头(8) 在 QML 测试表里但设备端无执行体。** 真机上
`miss` 由 `ViewFinished.qml:21-23` 的 `supportedItemsLive` 算出，命中
`SequentialTestPanel.qml:62-64` **自动记 fail「设备缺能力」**——9 项里 3 项直接判废。
对 Mock 却全过（2037 把这 3 位都置了 1）。

附带矛盾：设备端注册了 InfraredLight(1)，但 CS7G 是全彩夜视、**物理上没有 IR 灯**
（MockData 的注释与之相反）。协议保留供其他产品复用可以，但真机会声称一个不存在的能力。

**修法**：补 4/6/8 三个执行体（不是替换假实现——产测域本来就没有假实现），
或把这 3 项从产品 profile 的测试表里摘掉。两条路都行，但**必须与 mock 的 2037 对齐到同一个值**，
否则 Mock 与真机永远不一致。

### ③ 关机"报成功但不断电"的静默失败

**链路本身完整**：`product_test_service.cpp:348-359`（受理即回 `Code=0`）
→ `:223-230`（延时到点触发）→ `main.cpp:132-134`
→ `RequestMcuShutdown`（`aov_app_runtime.cpp:2369-2383`）→ power service 写 MCU 命令帧
→ OFF 在后续 PollBattery 快照锁存 → `main.cpp:257` 读 `IsMcuPowerOffRequested` 退主循环。

**失败路径**：`aov_app_runtime.cpp:409-416` 仅在 `runtime_services_.power` 非空时
置 `power_initialized_ = true`。为空时 `RequestMcuShutdown` 只 `fprintf(stderr)` 返回 false
——**而 PC 早在受理时就收到了 `Code=0`**。

⇒ MCU 链路不通时：**工位显示通过、设备不断电、PC 完全不知情。**

概率不低：`CMakeLists.txt:18` **`AOV_ENABLE_BATTERY_MCU` 默认 OFF**。

注：PC 侧"受理即完成、不等真断电"是**写明的契约**（`cloud_client.hpp:67-69`），
不是编码错误。但该设计假定 MCU 通路可用，而没有任何环节验证这个假定、
也没有任何环节在它不成立时回报。

### ④ 待真机验证：LastUpdate 单位

`cloud_client.cpp:91-96` 的 `heartbeatAgeMs()` 把 `PtestHeartbeat.LastUpdate` 当**毫秒**：

```cpp
return QDateTime::currentMSecsSinceEpoch() - heartbeatLastMs_;
```

Mock 发的是毫秒（`mock_transport.cpp:62-70`），所以自测正常。
**若腾讯 `DescribeDeviceData` 返回的是秒**，age ≈ 56 年，超过任何窗口 ⇒ **恒判离线**。

未实机调用，无法确认。**接真机第一件事就验这个。**

雪上加霜：`heartbeatValue` / `heartbeatAgeMs` 两个属性**没有任何 QML 在用**
（`cloud_client.hpp:39-41` 声称"调试页与顶栏诊断用"，实际零引用）。
而这两个值恰好就是能让工人一眼看出"心跳年龄 = 56 年"的诊断信息。
**建议接真机前先把它们显示到云调试页**——改动很小，诊断收益很大。

### ⑤ 潜伏项：WriteIdentity 缓冲区

`tencent_generated_iv_usrex_callbacks.c:1921` 用 `char params[1024]`。
按物模型极值算（`iv_usrex.h:136-148` 的结构体尺寸与物模型 max 完全一致）：

```
值合计 127+31+127+127+191+191+127+15         = 936
键名+分隔符（sn= … request_id=）              =  93
分号 8 个 + request_id 最多 10 位             =  18
                                     合计   ≈ 1047 > 1024
```

`snprintf` 截断丢的正是**尾部的 `request_id`** ⇒ 回来 `RequestId=0` 永不匹配 ⇒ PC 超时。
实际值约 286 字节（SN≈20、密钥 b64≈44、UUID≈36），**暂不触发**。
但客户若用长 SN / 长 ProductKey 就会踩到，且症状与断点 ① 一模一样（超时无结果），
容易误判。建议顺手把缓冲改到 2048 并检查 `snprintf` 返回值。

## 6. 运维陷阱（不是 bug，但会误判）

### 6.1 返修设备重回调焦：搜得到、拉不了流

`product_test_mode` **开机时算一次** = "加密分区成品标识未写"
（`product_test_service.cpp:186-199`）。而：

- 发现应答**无条件启动**（`main.cpp:211`）
- RTSP **仅在 `product_test_mode` 为真时启动**（`main.cpp:216`）

⇒ **已过成品的设备（尤其维修返修后重回调焦）开机即 RTSP 关**：
PC 照样搜到并列在设备表里（因为发现照答），双击拉流却失败，且**没有任何提示指向真正原因**。

**解法**：维修工位先 `clearPartition`（`ViewRepair.qml:263`，会清阶段标识）**再重启**，
产测态才回来。**需要写进维修工位作业指导书**：重回调焦前必须"先清除 + 重启"。

### 6.2 产测态绕过低电保护

`aov_work_mode_state_machine.cpp:32-34` 把 `product_test_active` 判在**最前**，
直接 `return AwakeNormal`，**排在低电保护之前**。

设计理由写在注释 `:29-31`：产线台架电池不可靠（假电/空电），低电保护掐断产测会卡整批工位，
真实电量由 PC 经电池测试项监控。量产固件本位恒 false，低电保护语义不变。

⚠️ **副作用**：产测态持续到成品标识写入为止 ⇒ **真电池上跑且迟迟不过站的设备会一路放电到耗尽**。
产线需要留意长时间滞留工位的设备。

（注：早先记录的"设备端产测仅在常电模式下可用"说法**方向是反的**——是产测态自己强制常电。）

### 6.3 重复下发防护：模式不统一但无 bug

只有 `ViewCloudDebug.qml` 绑 `CloudClient.busy`（7 处）。四个生产工位视图各用自己的局部闸：

| 视图 | 闸 | 代码行 |
|---|---|---|
| ViewFocus | `writeReqId < 0` | `:227` |
| ViewFinished | `chainBusy` | `:381, :401` |
| ViewInspect | `writing` + `done` | `:287` |
| ViewRepair | `archived` | `:99, :173` |

各自能防住自己的重复下发，**没有排队堆积的 bug**。只是没有统一收口——
新加工位页时容易漏，建议后续统一到 `busy`。
