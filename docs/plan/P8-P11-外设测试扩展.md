## P8 · 4G 双 SIM 逐槽检测

Item=9 从一条指令拆成**三条串行**：

| 顺序 | 指令 | 说明 |
|---|---|---|
| 1 | `(Op=0, Param1=0)` | 当前槽 |
| 2 | `(Op=0, Param1=1)` | SIM0 槽 |
| 3 | `(Op=0, Param1=2)` | SIM1 槽 |

**必须串行**（评审表 §2.5 硬约束 1：设备端结果单槽，并发必丢结果）。
每条等到自己的 `RequestId` 回来或超时，再发下一条。

### 超时特例：≥90 秒

逐槽检测里设备要原子完成「切槽 → 测 → 切回原槽」，**含最长 30 秒网络检测**。
通用超时（3 秒档）在这里必然误判。这是"单一超时值行不通"最极端的例子 ——
从 LED 的 500ms 到这里的 90s，跨度 180 倍。

### 判定（在 PC）

- `sim=absent` 是 **Code=0 的事实上报**，不是错误。治具双槽都插卡时它意味着卡座
  异常 → 判不良。**别把它当成"设备说没事"放过去**。
- `bars` 阈值默认 ≥2，进 profile 可配（`thresholds.cellBarsMin`）——
  老产测软件就是 csqval1/csqval2 双标准，产线不同批次要求会变。
- detail 带 `,restore_failed`（Code=2）→ **切槽没切回来**，设备留在错误槽位。
  这条要红警提示**停线检查**，不是普通失败 —— 后续所有设备都可能受影响。

### UI

成品页 4G 那一行拆成两个子结果（SIM0 / SIM1），各自独立状态徽标。

## P9 · SD 读写校验

在位查询（`Op=0`）之后**串行追加** `Op=4, Param1=1`（写 1MB 校验）。超时 30s。

判定：`verify=ok` **且** `write/read` 速率 ≥ profile 阈值（默认宽松 write≥2 /
read≥5 MB/s，板验后收紧）。

`Code=2 + data mismatch` → 提示"卡座虚焊典型表现" —— 这个特征提示能省产线大量
排查时间，比单纯报"失败"有用得多。

⚠️ 不与维修页的分区清除混排在同一屏。两者都碰存储，UI 上放一起迟早有人点错。

## P10 · 纯 PC 三条（设备端零改动）

### ① 固件版本校验

profile 加 `expectedSwVersion` / `expectedHwVersion`，读 `ProductTestInfo` 比对，
不符判不良。

**放在进工位后的首次信息核对处，与 ProductId 准入同一个地方** —— 两者性质相同
（都是"这台设备是不是我要测的那台"），放一起工人只需理解一个概念。

### ② 外电检测

电池项（Item=5）做两步：查电量 → 提示工人接外电 → 再查一次，`external=1` 才过。

### ③ 喇叭+咪头回环，一步双验

P2P 拉流态下发喇叭放音（`Item=7, Op=4`），PC 端听到 = **喇叭✓ + 咪头✓ +
音频链路✓** 三项一次验完。

UI：调焦页现有的咪头卡升级成「放音并聆听」一个按钮 + 听到/没听到判定
（两个判定按钮已有二次确认）。

这条的价值是把两个人工项合成一个动作，产线每台省一次操作。

## P11 · profile schema v2

承载 P8–P10 的配置。在现有 `items` 之外增加：

```json
{
  "productId": "5KHBENFCX2",
  "name": "CS7GV1.0",
  "enabled": true,
  "items": [0, 1, 2, 5, 7, 9, 10],
  "expectedSwVersion": "V1.0.0.14",
  "expectedHwVersion": "A2",
  "thresholds": {
    "cellBarsMin": 2,
    "sdWriteMinMBps": 2,
    "sdReadMinMBps": 5
  }
}
```

**位图不动**：P8/P9 的扩展都在原 Item 编号内（9 和 10），不新增 bit，
所以 `SupportedItems` 仍是 0x6A7，`profile ∩ 设备能力` 的交集逻辑零改动。
这是刻意的设计选择 —— 位图一改，设备端、云端物模型、PC 三边都要动。
