## 3. 标记位分流（口径已定：或逻辑）

### 3.2 判定口径（2026-08-18 用户定稿）

**流程**：先读加密分区成品标识，**不管它是什么值，都再读一次工装卡的产测标识**。
任一为"未产测"即走产测流程：

```cpp
// 目标态伪码
bool ShouldEnterProductTestMode(store, card) {
    const bool finished = store.ReadStage(state).ok() && state.Completed(Finished);
    const bool card_says_done = card.present && card.ptest_done == 1;
    return !(finished && card_says_done);   // 两者都说"已产测"才跳过
}
```

即 **`产测态 = !成品标识已写 || 卡标识为 0`**。

**这样更灵活**：哪怕成品标识已经写了，只要把卡里 `ptestDone` 改成 0，
**这台机器依然会走产测流程**——返工重测不必先清加密分区，改卡即可。

真值表：

| 加密分区成品标识 | 卡标识 | 行为 | 场景 |
|---|---|---|---|
| 未写 | 0 | **产测** | 全新板 |
| 未写 | 1 | **产测** | 卡被提前置 1 / 卡复制错；保守起见仍测 |
| 已写 | 0 | **产测** | **返工重测（本口径的主要收益）** |
| 已写 | 1 | 原流程 | 正常出厂 |
| 未写 | 卡缺失/字段缺失 | **产测** | 保守方向 |
| 已写 | 卡缺失 | 原流程 | 客户手里的设备（无卡） |

### 3.3 两个边界情形必须区分

上表最后两行是**不同的**，实现时不能合并：

| 情形 | 判定 | 理由 |
|---|---|---|
| **文件根本不存在**（客户设备、无卡） | 回落到"只看加密分区" | 若把"无文件"当 0，则**每台出厂设备开机都进产测态**——绕过低电保护、强制常电、启动 RTSP。灾难性 |
| **文件存在但 `ptestDone` 字段缺失** | 当 0（未产测） | 卡是产线做的，字段漏了是做卡失误，多测一遍无害 |

> 注：量产固件 `AOV_ENABLE_PRODUCT_TEST=OFF`，整个产测域编译期消失，
> 上述判定根本不会执行。所以"无文件"这一行是**双保险**，不是唯一防线。
> 但双保险要留着——产线固件误流入市场是真实风险。

### 3.3b 标记位字段建议

`device_info.json` 当前解析 4 个字段（`provisioning_bootstrap.cpp:100-103`）：
`productId` / `deviceName` / `deviceSecret` / `region`（缺省 `"china"`）。

> **顺带纠正**：这是标准腾讯**三元组 + region**，你说的"三元组"是对的。
> 代码里 `provisioning_bootstrap.hpp:22` 那句注释写的"四元组字段缺失"**措辞有误**，
> 实际校验的是 3 个必填字段（`:106-113`），建议顺手改正以免后人误解。

工装卡文件目标形态（三元组 + 标识位 + **产测参数**，见 §5.7 为什么参数必须在这里）：

```json
{
  "productId":    "5KHBENFCX2",
  "deviceName":   "1000000003",
  "deviceSecret": "……",
  "region":       "china",

  "ptestDone": 0,

  "ptest": {
    "batteryMinPercent":   20,
    "autoFailRepeat":       0,
    "autoFailIntervalSec":  5,
    "manualTimeoutSec":   180,
    "manualNagRepeat":      3,
    "manualNagIntervalSec":30
  }
}
```

命名与取值口径：

- `ptestDone`：**0 = 未产测（走产测流程）、1 = 已产测（走原流程）**
- 字段缺失当 0；**文件整体不存在则回落到只看加密分区**（§3.3 的区分）
- 现有 `ExtractJsonString` 只取带引号的字符串值（`provisioning_bootstrap.cpp:17-29`），
  **读不到裸数字**。需补 `ExtractJsonInt`，建议两种写法都认（`0` 与 `"0"`），
  宽松解析与现有风格一致
- 嵌套 `ptest` 对象：现有 `ExtractJsonString` 是"按键名找第一个带引号的字符串值"的
  平铺扫描（注释 `:14-16` 明说平铺与嵌套两种布局都认），所以**嵌套键名唯一即可正常取到**，
  不必写 JSON 解析器。但键名不能与外层重名

### 3.4 常电模式：已实现，但有个副作用要知道

你说"产测流程在常电模式下进行"——**已经是强制的**，且比"可用"更强：
`aov_work_mode_state_machine.cpp:32-34` 把 `product_test_active` 判在**最前**，
直接 `return AwakeNormal`，**排在低电保护之前**。理由写在注释 `:29-31`：产线台架电池
不可靠（假电/空电），低电保护掐断产测会卡整批工位。

⚠️ **副作用**：产测态**绕过低电保护**。产测态持续到退出条件满足为止 ⇒ 真电池上跑且
迟迟不过站的设备会**一路放电到耗尽**。这也是 §3.2 建议方案 B 的一个理由：
若用方案 A 且卡被误复制，一台已出厂机器可能被拉回产测态并绕过低电保护。

## 4. 文件模式改造（SD 挂不上的临时方案）

好消息：**基本是配置问题，不是重写**。`ProvisionOptions`（`provisioning_bootstrap.hpp:34-41`）
已经把路径拆成可配项：

```cpp
struct ProvisionOptions {
    std::string mount_point {"/mnt/sdcard"};      // ← 改这里
    std::string file_name {"device_info.json"};
    std::string expected_product_id;
    bool try_mount {true};                        // ← 文件模式置 false
};
```

### 4.1 唯一需要改代码的地方

`provisioning_bootstrap.cpp:79-83`：读不到文件时先查卡在不在位——

```cpp
if (!ReadTextFile(path, text)) {
    if (!CardPresent()) {
        return Make(ProvisionStatus::NoCard, "sd card absent");   // ← 文件模式下会误报
    }
```

文件模式下没有 SD 卡，`CardPresent()` 恒 false ⇒ **无论文件读没读到都先报 NoCard**，
播「请插入工装卡」，掩盖真正的路径问题。

**改法**（保留 SD 逻辑，加一个模式开关）：

```cpp
struct ProvisionOptions {
    // ……现有字段……
    // 卡在位检查与挂载重试。文件模式（SD 挂不上的临时方案）置 false：
    // 直接按普通路径读，读不到即 FileMissing，不误报 NoCard。
    bool use_sd_semantics {true};
};
```

`:79-96` 改为 `if (options.use_sd_semantics) { ……现有 CardPresent/MountSDCard 分支…… }`
`else { return Make(ProvisionStatus::FileMissing, path + " not readable"); }`。

**SD 卡代码原样保留**，环境就绪后把 `use_sd_semantics` 改回 true 即可，无需回滚任何东西。

| 项 | 建议 | 理由 |
|---|---|---|
| 文件路径 | 复用已有持久化目录：`AOV_CONFIG_PERSIST_DIR`（`/var/appconfig/battery_ipc`），文件名沿用 `device_info.json` | 该目录已在 `main.cpp:90` 用作配置持久化，必然可写可读，不必新造路径约定 |

> **保留不动**：人工项的映射存在但永不触发，无害；后续产品若有自动化的灯/云台检测，
> 映射已就位。**只是不必现在录音。**

### 5.6 自动项失败：循环播报（用户 2026-08-18 新增）

自动检测项失败后**循环播报直到人工干预**，不是播 5 遍就停。

现有实现是固定 5 遍（`product_test_service.cpp:58-71` 的 `VoiceClipRepeat` 对错误类
`return 5`），播放间隔在调用点硬编码 1000ms（`main.cpp:145` 第三参）。

**好消息**：间隔本来就是 `PlayProductTestClip(file, repeat, interval_ms)` 的参数，
不是写死在播放器里的，改成可配只需把常量换成配置读取。

| 参数 | 含义 | 建议默认 | 取值约定 |
|---|---|---|---|
| `autoFailRepeat` | 循环次数 | **0** | **0 = 无限循环**（直到工人处理/设备关机）。>0 = 播指定遍数后停 |
| `autoFailIntervalSec` | 两遍之间的间隔 | 5 | 秒；比现在的 1s 拉长，避免连续轰炸 |

「一直播报」用 `autoFailRepeat = 0` 表达。**但无限循环必须有退出条件**，否则设备
在无人工位上会一直响到电池耗尽（产测态还绕过低电保护，§3.4）。建议退出条件取三者之一先到：

1. 该项被重新下发并通过
2. 设备收到 `PtestShutdown`
3. **电量跌破 `batteryMinPercent`** → 转入 §5.8 的低电关机流程

### 5.7 ⚠️ 配置从哪来：不能放 PC 端 factory_config.json

**这是本次评估最先要纠正的一处设计错误。**

上述参数**全部作用在上云之前或上云失败时**：低电量门在进产测态那一刻、4G/SIM/网络/云失败
播报在建连过程中。而 PC 端 `dist/factory_config.json` 的值要经
**PC → 云 → 设备** 才能到设备手上——**上云之前设备根本拿不到**。

这与三元组是**同一个先有鸡问题**：正因如此三元组才要放工装卡。

**结论：产测语音参数必须和三元组放在同一个文件里（工装卡）。**

| 参数 | 生效时机 | 能否走 PC 配置 |
|---|---|---|
| `batteryMinPercent` | **进产测态那一刻**，远早于上云 | ❌ 不能 |
| `autoFailRepeat/IntervalSec` | 自动项失败，可能发生在上云失败时 | ❌ 不能（上云失败时尤其需要） |
| `manualTimeoutSec/NagRepeat/NagIntervalSec` | 人工判定阶段，此时已上云 | 技术上可以，但**不建议拆散** |

最后一行值得解释：人工判定阶段 PC 确实已连上，参数可以从 PC 下发。
但**把六个同类参数拆到两个来源**会让现场排查变成噩梦（"这个超时是卡里的还是 PC 里的？"）。
**六个参数全放工装卡**，PC 端 `factory_config.json` 里**不要**出现产测语音参数。

> 另一条路：人工项超时提醒**由 PC 主动触发**——PC 侧计时，超时后下发
> `PtestPeripheralTest(Item=7 喇叭, Operation=4 执行)` 让设备出声。
> 这样设备端零改动、参数纯留 PC 侧。但语义上是"拿喇叭测试项当提醒用"，
> 且与真正的喇叭测试结果混在一条 `ProductTestResult` 里。**不推荐，仅备录。**

### 5.8 低电量门与关机流程（用户 2026-08-18 新增）

**进产测模式后先检测电量**，低于阈值则播报语音、**语音播完进关机流程**。

设备端已有现成件，不必新写：

| 需要的能力 | 现成实现 |
|---|---|
| 读电量百分比 | `peripheral_executors.cpp` 的 `RunBattery`（`common/battery.h`），已有 `ClampPercent`（`:24-28`） |
| 关机 | `RequestMcuShutdown()`（`aov_app_runtime.cpp:2369-2383`），产测关机已在用 |
| 播报 | `PlayProductTestClip(file, repeat, interval_ms)` |

设计要点：

- 阈值 `batteryMinPercent` 默认 **20**，来源工装卡（§5.7）
- 检测时机：**判定为产测态之后、上云之前**。理由：电量不足就没必要建连了，
  且此刻已强制常电（`AwakeNormal`），再拖只是多耗电
- 新增语音 `ptest_err_lowbat.aac`「电量过低，即将关机」，**播 1 遍**（不是 5 遍——
  要立刻关机，没时间循环）
- **必须等语音播完再关机**。`PlayProductTestClip` 若是异步投递，直接调
  `RequestMcuShutdown()` 会把声音掐掉。需要按 clip 时长延时，
  或复用 `PtestShutdown` 已有的延时关机机制（`product_test_service.cpp:356`
  的 `pending_shutdown_at_ms_`），给一个足够播完的 `delay_sec`（建议 10s）
- ⚠️ 关机依赖 MCU 链路。若固件未开 `AOV_ENABLE_BATTERY_MCU`，
  `RequestMcuShutdown` 返回 false 且**只打 stderr**——语音播了但机器不关。
  详见《产测链路端到端核对报告》§3③

### 5.9 人工项超时提醒（用户 2026-08-18 新增）

工人迟迟不判定 → 播报提醒，避免设备白耗电。

| 参数 | 含义 | 建议默认 |
|---|---|---|
| `manualTimeoutSec` | 进入判定态后多久没结果算超时 | 180（3 分钟） |
| `manualNagRepeat` | 提醒播几轮 | 3 |
| `manualNagIntervalSec` | 每轮间隔 | 30 |

新增语音 `ptest_wait_judge.aac`「请确认测试结果」，提示类音色（不是错误音）。

**实现位置有个坑**：设备端**不知道"正在等人工判定"**——人工项设备只回"指令已执行"
（`MockData.qml:83-85`），发完结果它就认为这条做完了。等待发生在 **PC 侧**
（`SequentialTestPanel.qml` 的 `phase === "judge"`）。

所以要么：

- **(a)** PC 侧计时，超时后下发指令让设备出声（§5.7 末尾那条备录方案）
- **(b)** 设备端自己判断"最近一条人工项指令回了结果后 N 秒内没收到新指令" → 播提醒。
  设备侧自洽、参数纯在卡里，但**误报风险**：工人正常操作间隔本来就可能超过 3 分钟
  （比如中途换料、接班）

**建议 (b)** 并把默认超时放宽到 180s 以上，理由与 §5.7 一致：参数集中在工装卡，
不拆两个来源。误报的代价只是多响一次，可接受。

## 5.10 语音文件放在工装卡里（用户 2026-08-18 补充）

语音文件随工装卡走，不烧进固件。好处明确：**换语音不用重新烧固件**，产线自己就能改文案。

但有两个必须处理的问题。

### ⚠️ 问题一：自举悖论——"请插入工装卡"这句话在工装卡上

卡不在位 → 读不到身份，**也读不到语音** → 播不出「请插入工装卡」。
工人只看到设备静默启动，什么提示都没有。同理 `ptest_err_cfgfile`（文件读不到）也无从播出。

**解法：分两级存放。**

| 组 | 存放位置 | 条数 | 理由 |
|---|---|---|---|
| **自举组** | **固件内置**（烧进去） | **3** | 卡/文件读不到时唯一能播的东西 |
| 其余全部 | 工装卡 | 23 | 卡已就位才会用到，可随卡更新 |

自举组就 3 条：

| 文件名 | 为什么必须内置 |
|---|---|
| `ptest_err_nocard.aac` | 卡不在位时播——不能放卡上 |
| `ptest_err_cfgfile.aac` | 文件读不到时播——不能放卡上 |
| `ptest_err_lowbat.aac` | 低电量门在**读卡之后但可能早于卡内语音可用**，且这条关系到设备是否安全关机，不能依赖外部介质 |

`ptest_err_quadruple.aac`（文件在但字段缺）与 `ptest_err_model.aac`（型号不符）
**可以放卡上**——此时卡已读到，卡上的语音也就能读到。

### ⚠️ 问题二：读卡时机早于音频子系统就绪

`main.cpp:74-76` 的注释已经点明这个约束：

> 失败不阻止启动——设备照常起来，**等 Start 后音频可用再播语音**提示工人
> （**此刻 libmedia 还没起，没有播放通路**）。

也就是说 provision 阶段的失败**现在就已经是延迟播报**的。语音文件搬到卡上不改变这一点，
但要注意：**卡在 provision 之后会被 DHFS 接管并重挂**（`main.cpp:73` 注释）。
若语音在播放时才去卡上读文件，可能碰上重挂窗口。

**解法**：provision 阶段把卡上语音**一次性拷到本地**（`AOV_CONFIG_PERSIST_DIR`），
之后播放只读本地副本。拷贝成本可控（26 条短语音，几百 KB 量级），
且顺带解决"卡被拔掉后语音还能播"的问题。

### 目录约定建议

```
工装卡/
  device_info.json          ← 三元组 + ptestDone + ptest 参数（§3.3b）
  voice/
    ptest_start.aac
    ptest_online.aac
    ……（23 条）
```

设备端：`<mount_point>/voice/<filename>` → 开机拷到
`AOV_CONFIG_PERSIST_DIR/voice/`；缺文件时回落固件内置（若有）或静默跳过并记日志。

**缺语音不能阻塞产测流程**——照 `product_test_log.cpp:31-33` 的既有纪律
（写日志失败只打日志不向上传播）。

## 6. 产测日志上云（本次唯一的大工作量）

### 6.1 现状与缺口

| 环节 | 现状 | 缺口 |
|---|---|---|
| 设备端本地存一份 | ✅ `product_test_log.cpp`，管道分隔 `时间戳\|请求号\|指令\|测试项\|结果码\|详情`，64KB 单次轮转（上界 2×64KB，不会写满 flash） | 无 |
| 记录内容 | **只记 `ResultRecord`**（云端下发指令的执行结果，`product_test_log.cpp:28-40`） | ❌ **起机阶段的失败不进日志**：provision 失败（`main.cpp:83-86`）、自检故障（`product_test_self_check.cpp:99`）**只打 stderr** |
| 上传到云端 | ❌ **完全没有** | 物模型 20 actions / 49 properties 无任何日志通道 |
| 到 PC 软件 | ❌ 无 | PC 侧无任何日志读取入口 |

**关键洞察**：PC 已经能通过 `ProductTestResult` 拿到**每条自己下发的指令**的结果
（含 Code 与 Detail）。所以"指令级失败"其实已经到 PC 了。
**真正缺的是"PC 没下发指令时发生的失败"**——起机 provision 失败、自检 4G/云异常。
这类失败恰恰是最需要日志的：此刻 PC 还没建连，屏上什么都没有，只有语音。

这个洞察决定了方案选型：**不必先做"整份日志文件上传"，先补"非指令类失败"这一小块，收益最大、改动最小。**

### 6.2 三种方案

| 方案 | 做法 | 改动量 | 优点 | 缺点 |
|---|---|---|---|---|
| **A. 新增只读属性 `PtestLastError`** | 设备把最近一条非指令类失败摘要写进属性；PC 现有轮询顺带读到 | **小**：物模型加 1 属性 + codegen + 一处上报；PC 侧 `InfoMapFromData` 加一行 | 复用现成的属性上报 + dirty 重试 + PC 轮询链路，**零新通道**；起机失败也能补报（dirty 机制在恢复在线后补发） | 只带摘要，不是整份日志 |
| **B. 新增属性 `PtestLogTail`（字符串，capped）** | 设备把日志尾部 N 行塞进字符串属性 | 中 | 能看上下文 | 属性长度有限（建议 ≤2KB），长日志要截断；PC 轮询频繁读大字符串会烧云 API 配额 |
| **C. 整份文件上传（COS/HTTP）** | 设备把 ptest.log 传到对象存储，PC 按 URL 下载 | **大** | 完整日志 | 设备需要 COS 凭证与上传实现；现有 `tencent_cloud_storage` 是**告警事件图片/视频**专用（绑 `iv_cs.h` 事件语义），**不能直接复用**；等于新建一条上传链路 |

**建议：先做 A，把 B 作为可选增强，C 暂不做。**

理由：A 用一个属性就把"PC 看不见的那段"补上了，且**完全走已验证的链路**
（属性上报 → dirty 重试 → PC 轮询 `DescribeDeviceData`），风险几乎为零。
而 C 的成本主要不在上传本身，在于要给产测态设备配一套对象存储凭证与生命周期管理——
产线现场排障用得上的信息量，A+B 已经覆盖，不值得为此新建一条链路。

### 6.3 方案 A 具体设计

**物模型新增只读属性**（v3 待加）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `Stage` | enum | 失败发生的阶段：0=provision 1=selfcheck 2=cloud 3=flash 4=info |
| `Code` | int | 复用 `ResultCodeValue` 口径 |
| `Detail` | string(maxlen 128) | 与语音对应的文本摘要，**纪律：绝不含 DeviceSecret**（照抄 provision 的 detail 纪律，`provisioning_bootstrap.hpp:28`） |
| `Ts` | int | epoch 秒 |

命名建议 `PtestLastError`（struct，只读），与 `ProductTestResult` 并列。

**设备端接入点**（三处，都已有现成的失败分支可挂）：

| 位置 | 现状 | 加什么 |
|---|---|---|
| `main.cpp:83-86` | provision 结果只 fprintf | 失败时同时写属性 + **写进 ptest.log** |
| `product_test_self_check.cpp:99-100` | 故障只 fprintf + 播语音 | 播语音处同时写属性 + 写 ptest.log |
| `product_test_log.cpp` | 只接受 `ResultRecord` | 加一个 `AppendEvent(stage, code, detail)` 重载，让非指令类失败也能落本地日志 |

**注意上报时序**：provision 失败往往意味着**上不了云**，属性写不出去。
这不是问题——`MarkPropertyReportDirtyLocked` 的 dirty 机制会在恢复在线后补发
（`tencent_cloud_service.cpp:3884-3889` 已有 `ProductTestResult`/`PtestHeartbeat` 的同款先例）。
但**型号不符/三元组无效这类失败是永久性的**，设备根本连不上云 ⇒ 属性永远发不出去。
**这类失败只能靠语音 + 本地日志**，云端拿不到，PC 也拿不到。这是物理限制，不是设计缺陷，
**必须在作业指导书里说明**：听到 `ptest_err_cloud` / `ptest_err_model` 时不要去 PC 上找记录。

**PC 侧改动**：`cloud_client.cpp` 的 `InfoMapFromData`（`:19-50`）加一段读 `PtestLastError`，
经现有 `infoUpdated` 信号送到 QML；云调试页加一栏显示。约 20 行。

### 6.4 顺带建议：把心跳两个属性也显示出来

`heartbeatValue` / `heartbeatAgeMs` 已在 `cloud_client.hpp:39-41` 定义并声称"调试页诊断用"，
但**没有任何 QML 在用**。做日志展示这一栏时顺手把这两个也放上去——
