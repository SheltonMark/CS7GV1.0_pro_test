按阶段分布：

| 阶段 | 项数 | 人日 | 内容 |

| SDK 对接 | 6 | 11 | 设备列表/状态/绑定解绑、指令下发、上报监听、拉流通道 |

## 2. 已做的 UI 在其中的位置

**「UI」在需求表里不是一个独立任务。** 唯一相关的是 R049「客户端工程框架与配置」
3 人日，开发内容写的是「搭建工程、配置管理、日志框架、**界面骨架**」——
界面骨架是这 3 人日里的一部分。

所以当前七页 UI（登录/产品门/调焦/准成品/成品/检查/维修/关于）对应的是
**R049 的界面骨架部分**，约占总量的 **4%**。其余 96% 是协议、编排、数据、报表。

这不是说 UI 做得不值——UI 定死了交互契约（谁在什么时候能点什么、错误怎么呈现），
后面 43 项都要往这个契约里填。但**必须清楚：现在看起来"软件差不多了"是错觉**。

具体差距，按需求表原项列：

| 需求表原项 | UI 有 | 真实业务缺 |
|---|---|---|
| R054 指令下发通道 | 流水面板（假数据） | 真实下发、超时、重试、结果回执 |
| R055 状态上报监听 | 结果徽标（假数据） | 订阅、解析、RequestId 认领、不丢事件 |
| R056/R066 拉流 | 占位块「XP2P 建联中」 | XP2P SDK + 播放（**最大未知**） |
| R057/R058 Excel/InputData 解析 | 无 | 整个文件解析层 |
| R059/R060 下发回读校验 | 无 | 写入 + 回读一致性 |
| R063–R065 三标识下发 | 按钮 + 二次确认 | 真实 PtestWriteStage |
| R081–R087 工位编排 | 步骤条（静态） | 流程引擎、异常中断、断点续测 |
| R088 数据采集存储 | 无 | SQLite 台账 |
| R089 IMEI/UUID 对应表 | 无 | 生成 + 导出 |
| R090–R092 报表/良率/导出 | 无 | 全部 |
| R093 Inputdata1/2 + **贴纸打印数据** | 无 | 全部（**P0，且是独立子系统**） |

**R093 值得单独提**：生成 Inputdata1（基于 UUID）、Inputdata2（含 IMEI）
及贴纸打印数据，验收标准是「文件格式满足打印系统」。这意味着要对接产线的
贴纸打印系统，格式由对方定。UI 里完全没有这个入口，需求表里它是 P0。

## 3. 需求表已过时的三处（评审表定稿后产生）

需求表 V2.3（08-11）早于评审表的一系列定稿（08-14），以下三处以**评审表为准**：

**① 没有「检查」工位。** 需求表只有调焦/成品/维修三个工位（R081–R087）。
但评审表 §4.10 已定稿检查是**第四个产测阶段**（Stage=4 + InspectTime），
且「四阶段时间戳齐全」是整机通过的最终判据。需求表需补检查工位的流程控制与
结果采集两项（参照 R081/R082 粒度，约 3 人日）。

**② R075 咪头测试指令已作废。** 评审表 §4.5 已定：咪头验收 =「PC 拉流软件里
能听到咪头附近声音」，走 P2P 音频通道人工判定，**设备端不需要单独指令**，
已从下发测试项移出。R075「下发咪头指令并判定通过/失败」按原样实现是错的。

**③ R070 日夜切换本产品不测。** 评审表已定：协议保留（面向后续产品复用），
但 CS7G 硬件不支持 IR-CUT，设备端不注册执行体、`SupportedItems` bit3 恒为 0。
R070 仍列 P0 1 人日，实际本产品无从验证。

另有一处**范围不一致**：R071 复位按键写「开机/关机/切换SIM卡/重置」四个功能，
评审表 §1.3 只定义了 `key=factory_reset` / `key=none`（10 秒超时等工人按键），
且注明**复位按键待 MCU 链路**。四功能验证的口径需要澄清。

## 4. 架构分叉：**必须先拍板**

需求表和已知事实冲突，这是最需要先解决的问题：

| 来源 | 说法 |
|---|---|
| 需求表 R050 | 「集成**腾讯云SDK**，封装认证、设备、通道基础能力」 |
| 需求表 R051–R053 | 设备列表查询、状态查询、**绑定/解绑**（典型云平台 API 语义） |
| 参考代码实测（kb §1） | **PC 不接腾讯云，接腾达自己的后台**。全仓无 `SecretId`/`TC3-HMAC`/`tencentcloudapi`；鉴权 = `Bearer access_token` + `sig:md5(...)` ⇒ **必须登录腾达账号** |
| 产测协议文档 | 走腾讯云 IoT **自定义透传 topic**（`.../ptest/down`、`/ptest/up`） |

三种说法互斥。这决定：

- **认证方式**（腾讯云密钥 vs 腾达账号登录 vs 设备证书）
- **R051–R053 是否存在**（若走透传 topic，设备读工装卡自行上云，评审表 §2.4
  没有 PC 侧绑定步骤——那么「设备列表/绑定/解绑」这 5 人日可能整块不需要）
- **P4 设置页里配的是什么凭证**（当前按「腾达后台账号」设计）

⚠️ 这不是实现细节，是**通信层的地基**。定错了 R050–R055 共 13 人日全部返工。
建议在写任何真实通信代码之前，与云端/后台同事确认一次。

## 5. 需求表没有、但产线一定需要的

- **操作者登录/角色/审计**（本轮新增需求，见 `docs/plan/`）——需求表无此项，
  但老产测软件有三级角色，产线换班与追责都依赖它。
- **台账落盘位置**（已定：与程序同目录）——R088「存储」没说存哪。
- **SN 编码规则**：`CS7GV1.0` + `2608150042` 直接拼成 `CS7GV1.02608150042`，
  型号段与流水号无边界、含点号会破坏 Excel/CSV/文件名。R092 导出要用到。
- **断点续测**：设备测到一半掉线/工人切走，回来能不能接着测？R083「异常可中断」
  只说了中断，没说恢复。

## 6. 建议的下一步

1. **先修 UI 的判定语义**（不依赖任何外部前置）：七项里指示灯/红外/白光/喇叭
   四项是**工人目视目听**，设备回 `ok` 只代表"指令执行了"。当前 UI 把 `Code=0`
   直接打绿✓ = 把"指令下发成功"伪装成"硬件合格"，灯不亮的机器会一路绿灯。
   准成品页与成品页都要改。
2. **拍板架构分叉**（§4）——阻塞 13 人日。
3. **更新需求表**至 V2.4：补检查工位、废 R075、标注 R070 本产品不测、
   澄清 R071 范围、补登录/角色/审计与台账位置。
4. 播放 spike（XP2P + Qt6 播放）仍卡三方库缺失，与上述并行。
